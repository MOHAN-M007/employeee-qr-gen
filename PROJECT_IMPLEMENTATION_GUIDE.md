# SSS Barcode ID Generator

## Complete Working and Implementation Document

This document explains how the current `sss_barcode_id_generator` project is organized, how it works end to end, and what is already implemented versus what is only partially wired.

## 1. Project Purpose

This is a Flutter application for She Software Solutions that allows a user to:

- enter employee or intern details
- generate a unique barcode-based employee ID
- preview the generated barcode
- save the barcode image to the device gallery
- view previously generated employee entries from Firebase Firestore
- edit or delete employee entries from the Firestore history screen

The app is primarily structured as a form-driven workflow with Firebase as the active backend data source.

## 2. High-Level Architecture

The main app flow is:

1. App starts
2. Firebase is initialized
3. Locally saved history is loaded from `SharedPreferences`
4. Dashboard screen opens
5. User navigates to the employee form
6. User fills the form and submits it
7. Barcode preview screen generates a unique employee ID
8. The employee record is saved to Firestore
9. User can download the barcode image to gallery
10. User can open history to see Firestore records in real time
11. User can update or delete a Firestore employee record

## 4. Core Files and Their Responsibilities

### `lib/main.dart`

This file bootstraps the application.

Current responsibilities:

- calls `WidgetsFlutterBinding.ensureInitialized()`
- initializes Firebase using `DefaultFirebaseOptions.currentPlatform`
- loads local history from `StorageService.loadHistory()`
- stores that local history in a global variable `generatedHistory`
- launches the app with `BarcodeApp`

Important note:

- `generatedHistory` is loaded but is not currently used by the dashboard, history screen, or preview screen
- the app currently uses Firestore for live history instead of the locally loaded list

### `lib/models/employee_model.dart`

This is the data model for employee information saved to storage and Firestore.

Current fields:

- `name`
- `role`
- `employeeId`

Current responsibilities:

- convert model to `Map<String, dynamic>` using `toMap()`
- build model from a map using `fromMap()`
- encode a list of employees to JSON
- decode a JSON string back into employee models

Important note:

- the form collects more information than this model stores
- `email`, `phone`, `address`, and `photo` are not part of `EmployeeModel`

### `lib/services/storage_service.dart`

This service manages local persistence using `SharedPreferences`.

Current responsibilities:

- save employee history under the key `employee_history`
- load employee history from `SharedPreferences`
- convert the list using `EmployeeModel.encode()` and `EmployeeModel.decode()`

Current status:

- this service is initialized from `main.dart`
- it is not actively used anywhere else in the current flow
- no screen currently saves to local history after barcode generation

### `lib/services/firestore_service.dart`

This service is intended to contain Firestore CRUD operations for employee records.

Implemented operations:

- `addEmployee(EmployeeModel employee)`
- `getEmployees()`
- `deleteEmployee(String docId)`
- `updateEmployee(String docId, String name, String role)`

Firestore collection used:

- `employees`

Document fields written:

- `name`
- `role`
- `employeeId`
- `timestamp`

Important implementation observation:

- `addEmployee()` and `getEmployees()` are inside the `FirestoreService` class
- `deleteEmployee()` and `updateEmployee()` are currently written after the class closing brace in the present file state
- because of that structure, the file appears inconsistent and may fail to compile unless the class structure is corrected
- `history_screen.dart` is calling `FirestoreService.updateEmployee(...)` and `FirestoreService.deleteEmployee(...)`, so those methods are clearly intended to be class methods

### `lib/screens/dashboard_screen.dart`

This is the home screen shown after app startup.

Current responsibilities:

- display app title and description
- provide navigation to:
  - `EmployeeFormScreen`
  - `HistoryScreen`

This screen acts as the central menu for the app.

### `lib/screens/employee_form_screen.dart`

This screen collects employee details from the user.

Current form inputs:

- employee name
- official email
- phone number
- role
- address
- photo upload from gallery

Validation implemented:

- name must not be empty
- email must not be empty and must contain `@`
- phone must not be empty and must have length 10
- role must be selected
- address must not be empty

Image handling:

- uses `image_picker`
- selects an image from the gallery
- displays selected image in a `CircleAvatar`

Submit behavior:

- validates form
- builds an `employeeData` map
- navigates to `BarcodePreviewScreen`

Important implementation observation:

- the selected photo is shown in the form screen only
- the photo is not passed into preview or saved to Firestore
- email, phone, and address are also not saved to Firestore in the current implementation

### `lib/screens/barcode_preview_screen.dart`

This screen generates and displays the barcode.

Current responsibilities:

- create a unique employee ID using the current timestamp:
  - format: `EMP<timestamp>`
- display:
  - card title
  - employee name
  - employee role
  - generated barcode
  - generated employee ID text
- save the employee record to Firestore
- allow barcode image download to gallery

Barcode generation:

- implemented with `barcode_widget`
- uses `Barcode.code128()`
- barcode data is the generated employee ID

Download flow:

- barcode widget is wrapped in `Screenshot`
- image bytes are captured using `ScreenshotController`
- image bytes are saved to gallery with `Gal.putImageBytes(image)`
- success feedback is shown through `SnackBar`

Important implementation observations:

- the Firestore save is triggered inside `build()` using `Future.microtask(...)`
- because `build()` can run multiple times, this pattern can potentially create duplicate Firestore records
- only `name`, `role`, and `employeeId` are saved to Firestore
- the employee data map contains more fields than the model actually persists

### `lib/screens/history_screen.dart`

This screen shows employee history from Firestore in real time.

Current responsibilities:

- listen to Firestore with `StreamBuilder<QuerySnapshot>`
- show loading indicator while data is loading
- show error state if stream fails
- show empty state if no employee records exist
- render records using `ListView.builder`
- allow edit and delete actions per record

Edit flow:

- opens `AlertDialog`
- pre-fills name and role
- updates Firestore on confirmation

Delete flow:

- opens confirmation dialog
- deletes Firestore document on confirmation

Data shown per record:

- employee name
- employee role

Important note:

- employee ID is stored in Firestore but is not displayed in the history list

### `lib/widgets/custom_textfield.dart`

Reusable text form field widget.

Responsibilities:

- wraps `TextFormField`
- standardizes label, border, validator, keyboard type, and max line behavior

### `lib/core/theme/app_theme.dart`

This file defines a custom theme using:

- pink primary color
- Google Fonts (`Cinzel` and `Montserrat`)
- Material 3 theme settings

Current status:

- the theme is defined but not currently applied in `main.dart`
- `main.dart` uses an inline `ThemeData(primarySwatch: Colors.pink)` instead

## 5. Firebase Integration

Firebase is integrated using:

- `firebase_core`
- `cloud_firestore`
- FlutterFire-generated `lib/firebase_options.dart`

### Initialization flow

In `main.dart`, the app calls:

```dart
await Firebase.initializeApp(
  options: DefaultFirebaseOptions.currentPlatform,
);
```

### Supported configured platforms

From `firebase_options.dart`, Firebase options are configured for:

- Android
- iOS
- macOS
- Web
- Windows

Important note:

- Linux is explicitly unsupported in the current Firebase config and throws `UnsupportedError`

### Firestore usage

Collection:

- `employees`

Read pattern:

- real-time stream ordered by `timestamp` descending

Write pattern:

- each new preview inserts a new Firestore document

## 10. Known Technical Risks in Current Implementation

### 1. Firestore save inside `build()`

Saving to Firestore inside `build()` can cause duplicate records if the widget rebuilds.

### 2. Incomplete Firestore service structure

The current file structure of `firestore_service.dart` suggests `deleteEmployee` and `updateEmployee` may be outside the class body. This should be verified and corrected if the app is failing to compile.

### 3. Data loss between form and storage

The form collects more data than the model and backend currently store.

### 4. Theme inconsistency

A richer theme exists in `AppTheme`, but the app currently uses a simpler inline theme.

### 5. Test mismatch

The widget test references `MyApp`, but the current app entry widget is `BarcodeApp`.

## 11. Suggested Real Implementation Improvements

If the project is to be completed to production level, the next logical improvements would be:

1. Move Firestore save logic out of `build()` and into a safer one-time lifecycle path
2. Fix `FirestoreService` method placement so all CRUD methods are clearly inside the class
3. Expand `EmployeeModel` to include email, phone, address, and optional photo path/url
4. Save selected image properly if photo support is required
5. Decide whether local history via `SharedPreferences` should remain or be removed
6. Apply `AppTheme.lightTheme` from `main.dart`
7. Clean the `README.md` merge conflict
8. Replace the default test with app-specific widget and service tests
9. Remove or document `temp_fix_project/` if it is no longer needed
10. Add explicit error handling around Firestore save and gallery export operations

## 12. Practical Summary

In its current form, the project already works as a basic employee barcode generator with Firestore-backed history management.

The real active implementation is:

- dashboard -> form -> preview -> Firestore save -> history list

The app is therefore best understood as a Flutter CRUD + barcode generation project with Firebase integration, where local storage and advanced export support were started or planned but are not yet fully connected to the live workflow.
